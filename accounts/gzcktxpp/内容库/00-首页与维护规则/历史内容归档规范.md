# 历史内容归档规范

This file is the single formatting standard for the final post-publication step: historical-content archiving.

Any AI or human collaborator handling archiving must read this file first. No other document may redefine archive fields, body structure, or archive boundaries.

## Archive Trigger Conditions

Write to the historical vault only when ALL conditions are met:

1. The user explicitly confirms the content was actually published or updated.
2. The user explicitly requests “确认写入知识库”, “确认归档”, or an equivalent archive instruction.
3. The actually used title, body, and publication date can be uniquely identified.

Content with only a confirmed topic or draft must NOT enter the historical vault. Unpublished content belongs in `03-选题规划`.

## File Location and Naming

- Directory: `内容库/01-历史内容/YYYY/YYYY-MM/`
- Filename: `YYYY-MM-DD｜内容标题.md`
- One video = one note.
- Before writing, check for identical or suspected duplicate files in the target directory. Never overwrite.

## Required Frontmatter

Every archive note must include:

- `title`
- `status`
- `publish_date`
- `business_line`
- `theme`
- `content_type`
- `audience`
- `pain_scene`
- `content_goal`
- `region`
- `platform`
- `series`
- `source`

Field rules:

- `title` must exactly match the published title.
- `publish_date` must use the actual publication date, not the archive-operation date.
- Prefer fixed values from [[固定选项库]] for `business_line`, `theme`, `content_type`, and `audience`.
- `pain_scene` must contain only one primary customer scenario; do not stack multiple pain points.
- `content_goal` must be a traceable knowledge-base objective, not promotional wording.
- `region` = `广州`; `platform` = `微信视频号`, unless project rules change.

## Required Body Structure

Write every historical note in this exact order. Keep only information useful for retrieval, reuse, and review:

```markdown
# 内容标题

## 内容概述

Use 2–4 sentences to explain what the content discusses, what judgment/problem it helps resolve, and its scope boundary.

## 目标客户

Describe the specific customer type, stage, or business status.

## 目标客户痛点场景

Describe in one paragraph what difficulty the customer faces, under what situation, and why this content is needed.

## 内容正文

Preserve the complete actually published body in original publication order. Do not rewrite facts or add unpublished content.

## 可延展选题

- 延展选题 1
- 延展选题 2

## 关联内容

- [[相关历史笔记标题]]
```

### Writing Boundaries

- Do NOT write “风险评估”. Risk checks belong to the copywriting stage, not historical knowledge storage.
- Do NOT add “一句话总结” or “一句话结论”. When summarization is needed, use “内容概述” with 2–4 sentences.
- Do NOT save multiple title options, backup titles, or the creation process. Keep only the title actually used.
- Do NOT include shot, visual, font, layout, or other production instructions.
- Do NOT fabricate publication data, customer feedback, policy conclusions, or cases.

## 可延展选题 Rules

- Keep 1–3 follow-up topics directly related to the original content but not repeating its conclusion.
- Each follow-up must connect to a business direction, customer scenario, or service opportunity.
- If no reliable extension exists, write `待根据发布后咨询问题补充`. Do not invent extensions.

## 关联内容 Rules

- Link only existing historical notes with a direct relationship in theme or customer scenario.
- Use Obsidian wikilinks: `[[文件标题]]`. Display text must match the target filename/title.
- Order related content by `前置主题 → 当前主题 → 后续主题` or by the same customer scenario.
- If no direct relation exists, write `暂无直接关联内容`. Do not fabricate links.

## Archive Completion Check

- [ ] Actual published title, body, and date confirmed.
- [ ] File path and filename follow the required format.
- [ ] Frontmatter is complete; fixed options do not mix synonyms.
- [ ] Body includes 内容概述、目标客户、目标客户痛点场景、内容正文、可延展选题、关联内容.
- [ ] No 风险评估、一句话总结、备用标题, or unpublished information included.
- [ ] No identical or suspected duplicate note exists.
- [ ] `_history-index.jsonl` 已增量更新，关联候选已按公共状态机更新；内容地图、月度复盘和缺口分析仅在明确要求时重建。
